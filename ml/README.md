# HopOrNot 예측 모델 계획

> 대상: 광역버스 1112 · M5107 · 5100 (경희대 국제캠퍼스 ↔ 서울)
> 프로젝트 유형: **Type A — 직접 학습** (scikit-learn, LightGBM, PyTorch)
> 작성: 2026-11-06

## 1. 한 줄 요약

버스가 **정류장 s에 도착할 때 남아 있을 좌석 수**를 4단계 확률로 예측하는 **순서형 다중분류 모델**을 직접 수집한 데이터로 학습한다. 출력 확률을 누적해 앱에서 "1석 / 5석 / 10석 이상 남을 확률"로 보여준다.

```
입력: 지금 이 버스의 상태(위치, 잔여석) + 노선·정류장·시간·수요 정보
출력: P(0석), P(1–4석), P(5–9석), P(10석 이상)
  → P(≥1석) = 1 − P(0석)
  → P(≥5석) = P(5–9석) + P(10석 이상)
  → P(≥10석) = P(10석 이상)
```

파인튜닝할 사전학습 모델은 쓰지 않는다. 데이터가 숫자로 된 정형·시계열 데이터라 처음부터 학습하는 트리 모델과 작은 신경망이 맞고, 데이터 수집부터 라벨 생성, 학습, 비교까지 모두 직접 한다.

## 3. 정답(라벨) 만들기

### 3.1 정류장 분류 (`stops.py`)

핵심 단위는 **(정류장, 버스)**다. 어떤 정류장에 올 어떤 버스가 몇 석 남아 도착할지를 맞힌다.

- **체크포인트**: 이름에 `(경유)`가 붙고 2025 일평균 승하차가 10명 미만인 곳. 고속도로 TG·JC·IC처럼 문이 열리지 않는다. 이름만으로 거르지 않는 이유는 `(경유)` 표기에도 실제 승차가 있는 곳이 있기 때문이다.
- **경희대 안쪽**: 학생 위주 정류장이라 뺀다. 서울행은 `경희대학교`에서 시작하고 영통행은 `경희대정문`에서 끝난다고 본다.
- **방향**: 회차 지점이 아니라 **고속도로**로 나눈다. 퇴근길 신논현처럼 회차 전 서울 정류장의 승객도 영통으로 가기 때문이다.

| 노선 | 서울행 (출발권) | 영통행 (서울권) | 영통행 (도착권) |
| --- | --- | --- | --- |
| 1112 | 5 – 14 | 22 – 49 | 57 – 67 |
| M5107 | 4 – 10 | 27 – 37 | 54 – 61 |
| 5100 | 4 – 13 | 25 – 35 | 46 – 56 |

체크포인트와 경희대 안쪽은 예측 대상에서 빠지지만 관측은 버리지 않는다. 위치 추적에 쓰고, 체크포인트의 잔여석은 다음 정류장의 도착 잔여석 라벨로 쓴다. 체크포인트끼리 이동할 때 좌석이 그대로인 비율이 96.8%다 (2026-11-05 ~ 06 관측).

**핵심 구간** (평일, 주 평가 대상):

| 이름 | 방향·구역 | 시간 |
| --- | --- | --- |
| 출근 | 서울행 출발권 | 07 – 09시 |
| 퇴근 | 영통행 서울권 | 17 – 22시 |

### 3.2 운행과 도착 잔여석 (`build_trips.py`)

같은 차량의 관측을 시간 순으로 잇고, 순번이 5 넘게 줄거나, 30분 넘게 비거나, 30 넘게 뛰면 새 운행으로 본다. 회차에서는 끊지 않는다.

예측 대상 정류장 s의 도착 잔여석은 아래 순서로 정한다.

| source | 규칙 | 비중 |
| --- | --- | --- |
| `arrival` | s에서 `state_cd = 1`(도착)로 관측 | 20.0% |
| `leg` | 직전 실제 정류장을 떠난 뒤의 관측. 문이 안 열리는 구간이라 도착 잔여석과 같다고 본다 | 40.7% |
| `range` | 앞뒤 관측의 범위. 사이 구간의 승차·하차 중 작은 쪽이 큰 쪽의 20% 이하일 때 | 33.5% |
| `mixed` | 앞뒤 관측의 범위지만 승하차가 섞여 범위를 벗어날 수 있음. 항상 애매한 라벨 | 5.8% |

```
18:02  정류장 3 출발  14석
       (정류장 4, 5 관측 없음)
18:04  정류장 6 출발  11석
→ 정류장 4, 5 도착 잔여석은 11 ~ 14석
→ 단계로는 "10석 이상" 확정
```

범위가 단계 경계에 걸치면(예: 3 ~ 7석) **애매한 라벨**로 표시하고, 학습에서는 제외하거나 가중치를 낮춘다. 비율은 보고서에 데이터 품질 지표로 남긴다. 회귀 비교를 위해 단계뿐 아니라 좌석 범위(`seats_low`, `seats_high`)도 저장한다.

**규칙 검증** (직접 관측된 도착을 가리고 규칙으로 맞힘, 2026-11-05 ~ 06):

| 규칙 | 결과 |
| --- | --- |
| `leg`, 서울행 출발권 | 좌석 일치 92.2%, 단계 일치 100% |
| `leg`, 영통행 서울권 | 좌석 일치 68.4%, 단계 일치 96.1% |
| `leg`, 영통행 도착권 | 좌석 일치 67.9%, 단계 일치 97.3% |
| `range`, 한 방향 구간 | 실제 값이 범위 안 93.9% |
| `mixed` | 실제 값이 범위 안 73.1% |

하차가 많은 정류장의 `arrival` 관측은 일부 하차가 반영되어 직전 값보다 큰 경우가 많다.

### 3.3 단계

| 단계 | 잔여석 | 의미 |
| --- | --- | --- |
| 0 | 0석 | 만석, 탈 수 없음 |
| 1 | 1 – 4석 | 줄이 길면 못 탈 수 있음 |
| 2 | 5 – 9석 | 대부분 탑승 가능 |
| 3 | 10석 이상 | 여유 |

만석(0단계)은 드문 사건이라 클래스 불균형을 고려한다 (6장 참고).

## 4. 학습 샘플

### 4.1 실시간 예측 (주 모델)

"예측 시점 t에, 정류장 p에 있는 차량 v가, 앞으로 지날 정류장 s에 도착할 때 몇 단계일까?"

- 하나의 관측(t, v, p)에서 **같은 운행의 앞쪽 예측 대상 정류장 s마다** 샘플을 하나씩 만든다. 회차를 넘어도 된다.
- 정답은 3장에서 만든 (v, s)의 도착 단계.
- 샘플이 많아지고 서로 비슷해지므로, 몇 정거장 앞까지 볼지(예: 실제 정류장 기준 최대 20개)와 관측 샘플링 간격을 정해 크기를 조절한다.

### 4.2 시간대 예측 (보조)

아직 출발하지 않은 버스, "19시 10분 이후에 출발하면 바로 탈 수 있나"에 답하는 용도. 현재 상태 특징 없이 시간·정류장·수요 특징만으로 학습한다. 실시간 모델이 완성된 뒤 같은 파이프라인에서 특징만 빼서 만든다.

## 5. 입력 특징

모든 특징은 **예측 시점 t까지 알 수 있는 값만** 쓴다 (미래 정보 누수 방지).

| 분류 | 특징 |
| --- | --- |
| 현재 상태 | 이 차량의 현재 잔여석, 현재 정류장 순번 p, 목표 정류장까지 남은 정류장 수 (s − p) |
| 노선·정류장 | 노선, 방향, 목표 정류장 순번 s, 목표 정류장 ID, 서울/경기 구분 |
| 운행 상황 | 앞차와의 시간 간격, 앞차가 목표 정류장을 지날 때(또는 지금) 잔여석, 같은 시간대 운행 대수 |
| 시간 | 시각 (30분 구간), 요일, 평일/주말/공휴일, 학기·방학·시험기간 |
| 평소 수요 | 2025년 같은 정류장 × 요일유형 × 시간대 평균 승차·하차 인원, p와 s 사이 정류장들의 평균 승차 합계 |
| 날씨 | 직전 1시간 강수량, 비·눈 여부 |

**구현 상태** (`features.py`): 날씨와 학기·시험기간을 뺀 특징을 구현했다. 날씨는 ASOS 자료를 받아야 하고, 학사일정은 확인이 필요하다. 서울/경기 구분은 구역(`zone`)으로 대신한다.

**미래 정보 규칙**: 앞차 기록은 `known_at`이 t 이전인 것만 쓴다. `known_at`은 도착했다는 사실과 값을 함께 알 수 있는 시각이고, 도착을 직접 보지 못했으면 다음 관측 시각이다. 어떤 시각 이후의 관측을 지우고 파이프라인을 다시 돌려도 그 이전 샘플의 특징이 그대로여야 한다.

## 6. 비교 모델

| # | 모델 | 라이브러리 | 수업 연결 | 역할 |
| --- | --- | --- | --- | --- |
| 0 | 과거 빈도 기준선 | 규칙 | – | 같은 노선·정류장·요일유형·30분 구간의 과거 단계 비율. "AI 없이" 기준 |
| 1 | 다항 로지스틱 회귀 | scikit-learn | 선형 분류 | 가장 단순한 학습 모델 |
| 2 | 랜덤 포레스트 | scikit-learn | 트리 앙상블 (배깅) | 배깅 계열 |
| 3 | **LightGBM** | lightgbm | 트리 앙상블 (부스팅) | **주 모델** |
| 4 | MLP → GRU | PyTorch | 딥러닝 | 지나온 정류장별 잔여석 순서를 입력으로 받는 시계열 모델 |
| 5 | 좌석 변화량 회귀 | lightgbm | 회귀 | 현재 → 도착 잔여석 변화량을 예측하고 오차 분포로 단계별 확률 계산. 주 모델 후보 |

- GRU 입력: 차량이 지나온 최근 k개 정류장의 (잔여석, 정류장 순번, 경과 시간) 시퀀스 + 5장의 나머지 특징.
- 데이터가 약 3주라 GRU가 트리 모델보다 낮게 나올 수 있다. 그 결과 자체를 "데이터 양에 따른 모델 선택" 근거로 보고서에 쓴다.

**모델 5 계산**: 예측 변화량 + 검증 세트의 오차 분포(몇 정거장 앞인지별)를 0 ~ 정원으로 자르고, 그 분포에서 P(≥1), P(≥5), P(≥10)을 구한다. 0 이하가 모두 만석으로 모여 만석 확률이 나온다. 검증 세트의 RPS와 P(≥1) Brier 점수가 둘 다 모델 3보다 좋으면 주 모델을 바꾼다.

**클래스 불균형 대응**: 클래스 가중치(`class_weight`, LightGBM `class_weight`/`is_unbalance`), 학습 후 확률 보정(검증 세트로 isotonic 또는 temperature scaling).

**순서 보장**: 4단계 확률을 누적해 "k석 이상 확률"을 만들므로 P(≥1) ≥ P(≥5) ≥ P(≥10)이 항상 성립한다.

## 7. 데이터 분할

무작위로 섞지 않고 **날짜로 나눈다**. 같은 날·같은 운행의 샘플이 학습과 테스트에 나뉘어 들어가면 성능이 부풀려지기 때문이다.

```
11/05 ────────── 11/19 │ 11/20 ── 11/23 │ 11/24 ── 11/27
       학습 (약 2주)     │  검증 (4일)      │  테스트 (4일)
                        │  조기종료, 튜닝,  │  모델 확정 후
                        │  확률 보정        │  마지막에 1번만
```

- 하루의 경계는 새벽 3시로 잡는다 (자정 넘어 운행하는 막차를 전날로 묶기 위해).
- **롤링 평가**: 1주 학습 → 다음 며칠 평가, 2주 학습 → 다음 며칠 평가 … 로 데이터 양에 따른 성능 변화를 본다.
- 테스트 기간은 최종 평가 전까지 열어보지 않는다.

## 8. 학습과 튜닝

- 손실 함수: **다중분류 로그손실 (교차 엔트로피)**
  `loss = − 평균 log P(정답 단계)`
- 학습 세트와 검증 세트의 손실을 반복(트리 수) 또는 에폭마다 기록하고, 검증 손실이 더 줄지 않으면 멈춘다 (early stopping).
- 기록할 곡선: 학습/검증 손실 곡선, 학습/검증 정확도 곡선.

| 모델 | 튜닝할 값 |
| --- | --- |
| 로지스틱 회귀 | 규제 강도 C |
| 랜덤 포레스트 | 트리 수, 최대 깊이, 리프 최소 샘플 수 |
| LightGBM | learning_rate, num_leaves, 반복 횟수(조기 종료), min_data_in_leaf, feature_fraction |
| MLP / GRU | learning rate, 은닉 크기, 층 수, 시퀀스 길이 k, 에폭, dropout |

튜닝은 검증 세트에서만 한다. 시도한 값과 결과를 표로 남겨 "튜닝 근거"로 쓴다.

## 9. 평가

### 9.1 지표

**주 평가 대상은 3.1장의 핵심 구간이다.** 도착 라벨의 93.3%가 10석 이상이고 핵심 구간 밖은 96%라서, 전체 평균이나 정확도는 모델 차이를 가린다. 주 지표는 핵심 구간의 macro-F1, RPS, P(≥1) Brier 점수다.

| 지표 | 보는 것 |
| --- | --- |
| 정확도, macro-F1 | 가장 확률 높은 단계가 맞았나 (가이드라인 요구) |
| 4×4 혼동행렬 | 어떤 단계끼리 헷갈리나 (가이드라인 요구) |
| 로그손실 | 확률 전체의 질 |
| RPS (순위 확률 점수) | 단계 순서를 고려한 오차. "0석"을 "10석 이상"으로 본 오류를 더 크게 벌함 |
| Brier 점수 | P(≥1석), P(≥5석), P(≥10석) 각각의 오차 |
| 보정 곡선 | "70%"라고 한 경우가 실제로 70% 맞았나 |

RPS (단계 K = 4, 예측 누적확률 F, 실제 누적 O):

```
RPS = 1/(K−1) × Σ_{k=1}^{K−1} (F_k − O_k)²
```

### 9.2 나눠서 보기 (오류 분석)

- 핵심 구간 (출근 / 퇴근) / 그 외
- 방향 (서울행 / 영통행)
- 몇 정거장 앞을 예측했나 (1–3 / 4–10 / 11 이상)
- 실제 만석(0단계)이었던 경우만
- 크게 틀린 사례를 골라 원인 분류 (배차 지연·몰림, 시험기간, 날씨, 애매한 라벨 등)

### 9.3 직접 만든 현장 테스트 세트

가이드라인의 "직접 만든 테스트 데이터"로 **현장 검증 30–50건**을 따로 만든다. 평일 퇴근 피크에 서울 쪽 주요 정류장(잠실역, 서울역·광교, 강남·신논현)에서 앱이 낸 확률과 실제 도착 버스의 잔여석(도착 시 관측)·탑승 여부를 기록한다. 줄 선 인원 때문에 자리가 있어도 못 탄 경우도 같이 적는다.

## 10. 서비스로 연결

| 앱 기능 | 계산 |
| --- | --- |
| 정류장별 탑승 확률 | 다음 차량별 P(≥1석), P(≥5석), P(≥10석) |
| 몇 대 보내야 하나 | n대 안에 탈 확률 ≈ 1 − Π_{i=1..n} (1 − P_i(≥1석)). 버스끼리 독립이라고 가정한 근사이며, 앞차가 만석이면 뒤차도 붐비는 상관관계 때문에 실제보다 낙관적일 수 있음을 표시 |
| 지금 타려면 어디까지 | 같은 방향으로 거슬러 올라가며 P(≥1석)이 기준(예: 80%) 이상인 첫 정류장 + 거리 |
| 여유 시간대 | 시간대 예측 모델로 하루 확률 곡선 |
| 과거 기록 | 모델과 별개로 DB의 실제 도착 잔여석을 그대로 보여줌 |

서빙: 학습한 모델을 파일로 저장 → FastAPI 추론 서버에서 로드 → Spring Boot API가 호출 → 앱.

```
│   ├── build_trips.py      # 관측 → 운행 → 정류장 도착 이벤트 (라벨, 애매함 표시)

│   ├── split.py            # 날짜 분할, 롤링 평가 구간
│   ├── train_baseline.py
│   ├── train_sklearn.py    # 로지스틱 회귀, 랜덤 포레스트

└── models/                 # 학습된 모델 파일 (.gitignore, 릴리스에만 첨부)
```

실행은 `ml/` 에서 한다:

```bash
conda env create -f environment.yml
conda activate hopornot-ml
cp .env.example .env && chmod 600 .env    # 서버 collector/.env 의 DB 값 입력

ssh -N -L 5432:127.0.0.1:5432 bus         # 다른 터미널에서 켜 둔다
python -m src.export_db --start 2026-11-05 --end 2026-11-27

python -m src.boarding2025
python -m src.stops
python -m src.build_trips
python -m src.features
```

- macOS에서 pip로 받은 torch와 LightGBM을 한 프로세스에서 쓰면 segfault가 나거나 멈춘다. 이 환경에서 둘을 pip로 다시 설치하지 않는다.
- `evaluate.py` 는 모델을 불러오지 않고 `data/predictions/` 의 예측 결과만 읽는다.

## 13. 리스크와 열린 질문

| 항목 | 대응 |
| --- | --- |
| 데이터 기간이 약 3주로 짧음 | 2025 승하차 1년치를 평소 수요 특징으로 사용, 롤링 평가로 기간별 성능 제시 |
| 만석 사례가 적음 | 4단계로 묶기, 클래스 가중치, 만석 사례만 따로 평가 |
| 수집 간격 때문에 정류장 누락 | 체크포인트 관측으로 정확한 라벨 확보, 범위 라벨, 애매한 라벨 비율 보고, 운영계정 트래픽 증가 신청 |
| 줄 선 인원 미반영 | "k석 이상 남아 도착할 확률"로 명시, 현장 검증에서 못 탄 사례 별도 기록 |
| 2025 ↔ 2026 정류장 변경 | 정류소 ID로 붙임. 승차 인원 기준 사실상 100% 연결 확인 |
| 버스 간 상관관계 | "몇 대 보내야" 계산이 근사임을 표시, 앞차 상태를 특징으로 넣어 일부 반영 |
| 하차 많은 정류장의 도착 라벨 | `arrival` 관측에 일부 하차가 반영됨. 앱 문구는 "남아서 도착"으로 유지하고 현장 검증에서 차이를 기록 |
| 열린 질문 | 몇 정거장 앞까지 예측할지 (최대 20?), 단계 경계(1/5/10석)가 이용자에게 맞는지, 발표 시간 8분/10분 확인 |
